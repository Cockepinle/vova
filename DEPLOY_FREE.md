# Бесплатный деплой PakLine

Для обновления уже опубликованного сайта используйте [порядок выпуска и отката](RELEASE_UPDATE.md).

## Схема

- Django-сайт: Vercel.
- База данных: Neon PostgreSQL или Supabase PostgreSQL.
- Фото и файлы: Cloudinary.
- Почта: SMTP через переменные окружения.

## 1. База данных

1. Зарегистрируйтесь на https://neon.tech или https://supabase.com.
2. Создайте PostgreSQL database.
3. Скопируйте connection string в формате `postgres://...`.
4. На Vercel добавьте его как `DATABASE_URL`.

## 2. Фото товаров

1. Откройте имеющееся окружение продукта в [Cloudinary Console](https://console.cloudinary.com/). Для нового сайта создайте окружение продукта.
2. В **Settings → API Keys** выберите активный серверный ключ с правом загрузки. Скопируйте connection URL в формате `cloudinary://<api_key>:<api_secret>@<cloud_name>`.
3. В **Vercel → Project → Settings → Environment Variables** добавьте `CLOUDINARY_URL` для Production. В Preview укажите ключ тестового окружения.
4. Для уже опубликованного сайта сохраните прежний `cloud_name` и префикс `media/`. Тогда записанные в базе ссылки продолжат указывать на те же объекты после деплоя.

Задайте отдельный `CLOUDINARY_URL` для каждого окружения Vercel. После изменения
переменной выполните новый деплой. Команда сборки Vercel и скрипт
`build_files.sh` проверяют наличие настройки и формат строки подключения.
Эта проверка не авторизуется у провайдера. Уберите прежние раздельные
`CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY` и `CLOUDINARY_API_SECRET` из настроек
этого приложения. В Preview проверьте также значения, заданные для конкретной
ветки. После деплоя загрузите небольшой PNG в CMS через «Общие медиа», откройте
HTTPS-ссылку файла и проверьте выбор этого изображения в форме категории.
Проверьте также загрузку с компьютера в форме категории. При отказе сверьте
статус API-ключа, права Upload API для используемого префикса и окружение
продукта в Cloudinary. Runtime Logs показывают тип ошибки провайдера без ключей.
CMS отправляет каждый файл отдельным multipart-запросом и оставляет неудачные файлы для повторной попытки. Лимит CMS на Vercel составляет 4 МБ на файл. Стандартный лимит Vercel в 4,5 МБ
относится ко всему запросу, включая поля формы. На сервере с постоянным диском
лимит CMS также составляет 4 МБ на файл. Лимит веб-сервера должен учитывать весь multipart-запрос.

Настройка Cloudinary применяется к новым загрузкам через Django `STORAGES`.
Существующие локальные записи сохраняют адреса через `MEDIA_URL`. При переходе
на Vercel отдельно перенесите локальные файлы, если для этих адресов нет
публичного файлового сервера. Скопируйте уцелевшие файлы из `MEDIA_ROOT` на
постоянный публичный HTTPS-сервер с сохранением относительных путей и задайте его
базовый адрес через `MEDIA_URL`. Старые ссылки `/media/<путь>` будут
перенаправляться на этот сервер. Новые загрузки продолжат идти в Cloudinary.
Если исходник утрачен, загрузите замену в существующую запись медиатеки,
чтобы сохранить её связи с товарами и страницами.

На сервере с постоянным диском можно оставить файловое хранилище, задать
`MEDIA_ROOT` для каталога на постоянном томе и `MEDIA_URL` для его публичного
адреса. При `DEBUG=0` этот адрес обслуживает веб-сервер или CDN. Django
раздаёт локальные файлы по `MEDIA_URL` в режиме разработки. У Django должны
быть права записи, у веб-сервера права чтения. Сопоставьте префикс URL с тем же
каталогом и проверьте HTTP-ответ оригинала и миниатюру после повторного деплоя.

## 3. Vercel

1. Загрузите проект в GitHub.
2. На https://vercel.com нажмите `Add New Project`.
3. Выберите репозиторий сайта.
4. В `Environment Variables` добавьте:
   - `DEBUG=False`
   - `SECRET_KEY`
   - `ALLOWED_HOSTS=ваш-домен.vercel.app`
   - `CSRF_TRUSTED_ORIGINS=https://ваш-домен.vercel.app`
   - `DATABASE_URL`
   - `CLOUDINARY_URL`
   - `EMAIL_HOST=smtp.gmail.com`
   - `EMAIL_PORT=587`
   - `EMAIL_USE_TLS=1`
   - `EMAIL_HOST_USER`
   - `EMAIL_HOST_PASSWORD`
   - `DEFAULT_FROM_EMAIL`
   - `MANAGER_EMAIL`
5. Выберите **Django** в Framework Preset. До первой сборки подготовьте схему по шагам ниже.

## 4. Миграции

Перед первой сборкой новой базы задайте `DJANGO_SKIP_DOTENV=1` и передайте
через окружение `SECRET_KEY` и прямой PostgreSQL URI как `DATABASE_URL`.
Для существующих данных сначала выполните [порядок выпуска и резервного копирования](RELEASE_UPDATE.md).

```bash
python -m pip install -r requirements.txt
python manage.py release_migrate
python manage.py release_migrate --apply
python manage.py release_migrate --verify
python manage.py createsuperuser
```

После проверки схемы запустите сборку Vercel. Для Preview используйте отдельную
подготовленную базу, тестовое хранилище и отдельные настройки почты.

Последние миграции синхронизируют рассчитанные розничные цены и отключают
онлайн-оплату и способы доставки, кроме самовывоза. Миграции сохраняют товары,
заказы, аккаунты и данные корзин; перед запуском сделайте резервную копию базы.

После этого панель управления будет работать с серверной базой.

При выпуске версии с миграцией `0045_product_attribute_exclusions` запустите `python manage.py release_migrate --apply` и `python manage.py release_migrate --verify` до сборки Vercel. Миграция создаёт таблицу для исключений полей в отдельных товарах.

После деплоя загрузите в медиатеку несколько файлов JPEG, PNG, WebP, GIF или ICO, найдите их по исходным именам и привяжите один к тестовому товару. Проверьте миниатюру и публичную карточку. После следующего развёртывания снова откройте тот же HTTPS-адрес и карточку.

## 5. API

Для живых данных из базы добавлены endpoints:

- `/api/categories/` — категории.
- `/api/products/` — товары.
- `/api/products/?category=slug` — товары категории.
- `/api/products/?hits=1` — хиты продаж.
- `/api/products/?q=поиск` — поиск.
- `/api/cart/` — текущая корзина пользователя или гостя.
- `/api/management/orders/` — список заказов для сотрудника.
- `/api/management/orders/<id>/` — заказ с составом для сотрудника/CRM.

API заказов доступно только авторизованным сотрудникам.
